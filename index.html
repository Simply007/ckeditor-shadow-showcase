CKEditor Shadow Showcase

Three independent style levels — 1 the surroundings (the host app's page styles), 2 the editor theme (toolbar, dropdowns, panels), 3 the content styles (the document inside the editing area). Mix any combination below and watch two identically configured editors react: the editor with Shadow DOM only ever changes when you change levels 2 or 3, while the twin without Shadow DOM also inherits whatever level 1 throws at the page. Booting CKEditor 5 from jsDelivr…

The dashed block and both editors render the same HTML. Same build, same configuration, same theme, same content styles — the only difference is the tree each copy lives in. Open devtools: the right editor sits under #shadow-root.

1 · Surroundings stay out

Page style sheets do not match elements inside a shadow tree. The host app's rules (p, h2, li…) restyle the document of the editor without Shadow DOM because it is page DOM; the shadow editor needs no counter-measures. Its floating UI is isolated the same way — it mounts in a dedicated shadow root at the end of <body> via config.ui.overlayContainer.

2 · Theme on the host, not :root

v49 declares its tokens on :root, :host, so a :root override never reaches an editor inside a shadow root — the :host declaration wins. Each theme writes its set onto every shadow host element plus <html> for the light-DOM editor. That placement matters: the foundation → semantic → component token chain resolves on those same elements, so a foundation override there re-flows through the whole chain (a scoped override anywhere else would not). The presets follow the official dark-theme example — surfaces, button labels, hover/selected states, focus ring with its shadow coordinates, widget borders, placeholder, links — and every palette is contrast-audited: content text ≥ 7:1; UI text, labels and links ≥ 4.5:1 (WCAG AA), in the dark themes as much as the light ones.

3 · Content styles per tree

Typography of the edited document is scoped to .ck-content and must be loaded into each tree that holds an editing area: a <style> in the shadow root for the shadow editor, one in the document for the light editor. Note the namespace split: the canvas surface belongs to the theme (--ck-color-base-background paints the editable area), while the document ink belongs to --ck-content-* (--ck-content-font-color defaults to a fixed #000). The themes here bridge the two, so a dark theme recolors the ink along with its canvas. Link color is a content-style concern too: v49 ships no .ck-content a rule, so the Default preset lets links inherit whatever a rule reaches the tree (the browser default with Shadow DOM, the host page's rule without), while the other presets set their own, blended with the theme's ink via color-mix() so one preset stays readable on light and dark canvases.

Put it in Salesforce: two ways

Both start the same: upload ckeditor5.umd.js (1.9 MB) and ckeditor5.css (0.2 MB) as static resources CKEditor5JS and CKEditor5CSS (Setup → Static Resources, Cache Control Public; well under the 5 MB per-resource limit). Grab them from the Online Builder ZIP or the npm package, as this page does. The Lightning theme preset above shows the editor dressed for either shell.

The documented way Visualforce page in an iframe

What the official guide covers (v49). Lightning embeds the page in an iframe, so the editor gets a plain browser document: everything this showcase does works unchanged. The cost: an iframe, no data binding to the record without extra plumbing, and Visualforce in a 2026 codebase.

  1. Create the Visualforce page. Setup → Visualforce Pages → New, check Available for Lightning Experience…, paste the code below.
  2. Embed it. Lightning App Builder → drag the Visualforce component onto a Lightning page and select your page.
ckeditorPage.page 
<apex:page showHeader="false" standardStylesheets="false" docType="html-5.0">
  <head>
    <!-- CKEditor 5 from static resources (Setup → Static Resources) -->
    <apex:includeScript value="{!$Resource.CKEditor5JS}"/>
  </head>
  <body>
    <!-- Shadow DOM host for the editor -->
    <div id="host"></div>

    <script type="module">
      const LICENSE_KEY = 'GPL'; // or your commercial license key

      // 1. Build ONE constructed stylesheet from the static resource; it will
      //    be adopted by every shadow root that holds editor UI.
      const cssText = await (await fetch('{!$Resource.CKEditor5CSS}')).text();
      const sheet = new CSSStyleSheet();
      sheet.replaceSync(cssText + '.ck.ck-editor__editable_inline{min-height:260px}');

      // 2. The editor's shadow root.
      const host = document.querySelector('#host');
      const shadow = host.attachShadow({ mode: 'open' });
      shadow.adoptedStyleSheets = [ sheet ];

      // 3. A dedicated overlay root for balloons/dialogs/tooltips, hosted at
      //    the end of <body> so no ancestor can clip it. It is a separate
      //    tree, so it adopts the same sheet (config.ui.overlayContainer).
      const overlayHost = document.body.appendChild(document.createElement('div'));
      const overlayContainer = overlayHost.attachShadow({ mode: 'open' });
      overlayContainer.adoptedStyleSheets = [ sheet ];

      // 4. Mount the editor inside the shadow root.
      const mount = document.createElement('div');
      mount.innerHTML = '<p>CKEditor 5 in a Shadow DOM, inside Salesforce.</p>';
      shadow.appendChild(mount);

      const { ClassicEditor, Essentials, Paragraph, Heading, Bold, Italic,
              Link, List, BlockQuote, Table, TableToolbar, Font } = CKEDITOR;

      ClassicEditor.create(mount, {
        licenseKey: LICENSE_KEY,
        ui: { overlayContainer },
        plugins: [ Essentials, Paragraph, Heading, Bold, Italic, Link,
                   List, BlockQuote, Table, TableToolbar, Font ],
        toolbar: [ 'undo', 'redo', '|', 'heading', '|', 'bold', 'italic', '|',
                   'fontSize', 'fontColor', 'fontBackgroundColor', '|', 'link',
                   'bulletedList', 'numberedList', '|', 'blockQuote', 'insertTable' ]
      }).catch(console.error);

      // 5. Theming. v49 declares its variables on ':root, :host', so overriding
      //    on :root does NOT reach an editor inside a shadow root — set the
      //    --ck-color-* variables on the shadow HOST elements instead
      //    (the editor host and the overlay host alike). SLDS-flavored example:
      const LIGHTNING_THEME = {
        '--ck-color-base-background': '#ffffff',
        '--ck-color-base-foreground': '#fafaf9',
        '--ck-color-base-border':     '#e5e5e5',
        '--ck-color-base-text':       '#181818',
        '--ck-color-base-text-light': '#706e6b',
        '--ck-color-base-hover':      '#f3f3f3',
        '--ck-color-base-selected':   '#d8edff',
        '--ck-color-base-active':     '#0176d3',
        '--ck-color-base-action':     '#0176d3',
        '--ck-color-focus-border':    '#0176d3',
        '--ck-color-interactive-focus-border': '#0176d3',
        '--ck-color-link-default':    '#0176d3'
      };
      for (const el of [ host, overlayHost ]) {
        Object.entries(LIGHTNING_THEME).forEach(([k, v]) => el.style.setProperty(k, v));
      }
    </script>
  </body>
</apex:page>

The page reuses this showcase's shadow-DOM wrapper: adopted stylesheets, a dedicated overlay container, themes on the shadow hosts. licenseKey: 'GPL' runs the open-source build under GPL terms — swap in your commercial key for production or premium features.

The native way a Lightning Web Component draft for review

No iframe, no Visualforce: a real LWC you drop on a record, app or home page, with the editor in its own open shadow root inside the component. That root is what buys the isolation: in Lightning Experience components render in synthetic shadow, where SLDS and page styles still leak in; they stop at a real shadow boundary. Not in the official guide and not yet run in an org: the checklist below is what to verify.

  1. Create the bundle force-app/main/default/lwc/ckEditor/ with the three files below (the resource names must match @salesforce/resourceUrl/…).
  2. Deploy and place it. Lightning App Builder → Custom → ckEditor. Listen to its change event from the parent to save detail.value.
ckEditor.html 
<template>
  <!-- Two manual containers: the editor's own open shadow root goes on the
       first, the overlay root (balloons, dialogs, tooltips) on the second. -->
  <div class="ck-lwc">
    <div class="editor-host" lwc:dom="manual"></div>
    <div class="overlay-host" lwc:dom="manual"></div>
  </div>
</template>
ckEditor.js 
import { LightningElement, api } from 'lwc';
import { loadScript } from 'lightning/platformResourceLoader';
import CKEDITOR5_JS from '@salesforce/resourceUrl/CKEditor5JS';
import CKEDITOR5_CSS from '@salesforce/resourceUrl/CKEditor5CSS';

const LICENSE_KEY = 'GPL'; // or your commercial license key

// Editor theme expressed in SLDS global styling hooks (with fallbacks), so the
// editor follows the org's theme/branding instead of a hard-coded palette.
const THEME = {
  '--ck-color-base-background': 'var(--slds-g-color-neutral-base-100, #ffffff)',
  '--ck-color-base-foreground': 'var(--slds-g-color-neutral-base-95, #f3f3f3)',
  '--ck-color-base-border':     'var(--slds-g-color-border-base-1, #e5e5e5)',
  '--ck-color-base-text':       'var(--slds-g-color-neutral-base-10, #181818)',
  '--ck-color-base-action':     'var(--slds-g-color-brand-base-50, #0176d3)',
  '--ck-color-base-active':     'var(--slds-g-color-brand-base-50, #0176d3)',
  '--ck-color-focus-border':    'var(--slds-g-color-brand-base-50, #0176d3)',
  '--ck-color-interactive-focus-border': 'var(--slds-g-color-brand-base-50, #0176d3)'
};

export default class CkEditor extends LightningElement {
  @api value = '<p>CKEditor 5 in its own open shadow root, inside an LWC.</p>';
  editor;
  booted = false;

  async renderedCallback() {
    if (this.booted) return;          // runs after every render; boot once
    this.booted = true;
    try {
      // 1. The UMD build via the platform loader (it does not load ES modules).
      //    Exposes the CKEDITOR global.
      await loadScript(this, CKEDITOR5_JS);

      // 2. ONE constructed stylesheet from the CSS resource; adopted by every
      //    root that holds editor UI. (loadStyle() would land in the document,
      //    where a shadow root cannot see it.)
      const cssText = await (await fetch(CKEDITOR5_CSS)).text();
      const sheet = new CSSStyleSheet();
      sheet.replaceSync(cssText + '.ck.ck-editor__editable_inline{min-height:260px}');

      // 3. Our OWN open shadow roots on the lwc:dom="manual" containers.
      //    LWS forces the component's root to mode "closed"; CKEditor needs an
      //    open one (it reads Element#assignedSlot to find what scrolls/clips it).
      const editorHost = this.template.querySelector('.editor-host');
      const overlayHost = this.template.querySelector('.overlay-host');
      const shadow = editorHost.attachShadow({ mode: 'open' });
      const overlayContainer = overlayHost.attachShadow({ mode: 'open' });
      shadow.adoptedStyleSheets = [ sheet ];
      overlayContainer.adoptedStyleSheets = [ sheet ];

      // 4. Theme on the shadow HOSTS (v49 declares tokens on :root, :host, so a
      //    :root override never reaches a shadowed editor).
      for (const el of [ editorHost, overlayHost ]) {
        Object.entries(THEME).forEach(([k, v]) => el.style.setProperty(k, v));
      }

      // 5. Mount, wire data out.
      const mount = document.createElement('div');
      mount.innerHTML = this.value;
      shadow.appendChild(mount);

      const { ClassicEditor, Essentials, Paragraph, Heading, Bold, Italic,
              Link, List, BlockQuote, Table, TableToolbar } = CKEDITOR;

      this.editor = await ClassicEditor.create(mount, {
        licenseKey: LICENSE_KEY,
        ui: { overlayContainer },
        plugins: [ Essentials, Paragraph, Heading, Bold, Italic, Link,
                   List, BlockQuote, Table, TableToolbar ],
        toolbar: [ 'undo', 'redo', '|', 'heading', '|', 'bold', 'italic', '|',
                   'link', 'bulletedList', 'numberedList', '|', 'blockQuote', 'insertTable' ]
      });
      this.editor.model.document.on('change:data', () => {
        this.dispatchEvent(new CustomEvent('change', {
          detail: { value: this.editor.getData() }
        }));
      });
    } catch (e) {
      console.error('CKEditor 5 failed to boot', e);
    }
  }

  disconnectedCallback() {
    this.editor?.destroy();
    this.editor = undefined;
  }
}

Review checklist (scratch org)

  1. Open root inside a closed one. Lightning Web Security forces every component's own shadow root to closed; CKEditor needs an open root because it reads Element#assignedSlot to work out what scrolls and clips it. Hence attachShadow({ mode: 'open' }) on the lwc:dom="manual" divs rather than mounting in the component root. Verify LWS lets a component attach a shadow root to its own manual node.
  2. CSS delivery. loadStyle() injects into the document, which a shadow root cannot see, so the recipe fetches the resource and adopts a constructed stylesheet. If fetch() of a static resource is restricted in your org, fall back to a <link rel="stylesheet"> created inside each shadow root.
  3. Overlay placement. The overlay root lives inside the component, not at the end of <body> (the component should not reach for document.body). Balloons and dialogs position by getBoundingClientRect(), so this works until an ancestor region clips with overflow: hidden; check the link balloon near the bottom of a record page.
  4. Leave shadowSupportMode alone. Native shadow for the component itself is still beta in mixed shadow mode, it is forced onto every descendant, and base components do not support it. The editor's own root gives you the isolation without it.
  5. Known upstream limit. Safari and Chromium do not report the direction of a mouse selection inside a shadow root, so a backward selection is treated as forward. No workaround; same in the Visualforce version.
